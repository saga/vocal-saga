# 2026-11-04

## 18:55 修复 s.sunxiunan.com 列表看不到 DB999 历史记录

**症状**：首页只显示 SW998（swdb998）的译文，DB999（vocal-saga）的历史记录消失。

**根因**：`lib/app.ts` 的列表查询走 `createD1FailoverDatabase`，它的 `all()` 是
「主库有结果就返回，不再问备用库」，不是合并。主库一旦有数据，备用库就永远读不到。
写入侧本来就是 SW998 优先、DB999 只做兜底，两个库的数据从此单向前进。

**改法**：
- `fetchListPage(databases, page)` 改成跨库合并：每库各取 `offset + PAGE_SIZE` 条，
  按 `created_at DESC, id DESC` 合并排序后切出目标页，`total` 相加。
  每库只取前 limit 条不会漏行——第 limit+1 行必然排在该库前 limit 行之后。
- 列表行带 `dbIndex`（1 起，对应 `getD1Databases` 顺序），备用库的链接写成
  `/article/:id?db=2`；主库保持 `/article/:id`，历史链接形态不变。
- `/article/:id` 支持 `?db=N` 定向到指定库。两库 id 各自自增，同号是不同文章，
  不带参数时仍按主库优先故障转移。

**顺带修的测试基建**：`ensurePageTranslationSchema` 上线后，四个测试文件的 D1 mock
缺顶层 `run()`（建表语句用），也缺 `PRAGMA table_info` 分支，导致 10 个用例一直是红的
（写入全部失败）。补上 `run` 与「PRAGMA 返回空列 → 走建表」后全部转绿。

**验证**：`tsc --noEmit` 干净；vitest 831/831 通过。新增 3 个跨库用例
（合并列表、来源链接、`?db=2` 定向）。部署需要用户自己 `wrangler login` 或提供
`CLOUDFLARE_API_TOKEN`——本机没有可用凭据。
