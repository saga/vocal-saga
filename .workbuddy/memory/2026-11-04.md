## 18:55 修复 s.sunxiunan.com 列表看不到 DB999 历史记录

**症状**：首页只显示 SW998（swdb998）的译文，DB999（vocal-saga）的历史记录消失。

**根因**：`lib/app.ts` 的列表查询走 `createD1FailoverDatabase`，它的 `all()` 是
「主库有结果就返回，不再问备用库」，不是合并。主库一旦有数据，备用库就永远读不到。
写入侧本来就是 SW998 优先、DB999 只做兜底，两个库的数据从此单向前进。

**改法**：
- `fetchListPage(databases, page)` 改成跨库合并：每库各取 `offset + PAGE_SIZE` 条，
  按 `created_at DESC, id DESC` 合并排序后切出目标页，`total` 相加。
  每库只取前 limit 条不会漏行——第 limit+1 行必然排在该库前 limit 行之后。
- 列表行带 `dbIndex`（1 起，对应 `getD1Databases` 顺序），备用库的链接写成
  `/article/:id?db=2`；主库保持 `/article/:id`，历史链接形态不变。
- `/article/:id` 支持 `?db=N` 定向到指定库。两库 id 各自自增，同号是不同文章，
  不带参数时仍按主库优先故障转移。

**顺带修的测试基建**：`ensurePageTranslationSchema` 上线后，四个测试文件的 D1 mock
缺顶层 `run()`（建表语句用），也缺 `PRAGMA table_info` 分支，导致 10 个用例一直是红的
（写入全部失败）。补上 `run` 与「PRAGMA 返回空列 → 走建表」后全部转绿。

**验证**：`tsc --noEmit` 干净；vitest 831/831 通过。新增 3 个跨库用例
（合并列表、来源链接、`?db=2` 定向）。部署需要用户自己 `wrangler login` 或提供
`CLOUDFLARE_API_TOKEN`——本机没有可用凭据。

## 19:45 列表页增加「删除记录」按钮

**入口**：列表页每条记录一个删除按钮；页脚「设置管理密钥」可预置/清除密钥。
密钥就是 `AUTH_KEY`（`.dev.vars` 有，生产走 `wrangler secret`），只存 `sessionStorage`，
不写进列表 HTML，也不进 URL。点击先 `confirm`，再 `DELETE` 带 `Authorization: Bearer`。

**后端**：`DELETE /api/translations/:id?db=N`，挂在既有 `requireAuth` 上。
- 必须带来源库：两库 id 各自自增，同号是不同文章，走 failover 会删错库。
- `app.use('*', cors())` 是全局的，因此额外校验 `Origin` 必须等于 `c.req.url` 的
  origin；浏览器 fetch 必带 Origin，命令行（无 Origin）仍由 AUTH_KEY 把关。
- 用 `run()` 返回的 `meta.changes` 判断是否真的删到行，0 行回 404。

**测试**：mock D1 的 `bind().run()` 补 DELETE 分支并返回 `meta.changes`；
新增 6 例（按钮渲染含 db 序号、无/错密钥 401、跨站 403、同源放行、定向删备用库、
非法参数与不存在 id）。vitest 837/837。

**部署状态**：本机 wrangler 仍未登录（`Not logged in`），需要用户
`wrangler login` 或提供 `CLOUDFLARE_API_TOKEN` 后 `npm run deploy:cf`。

## 19:58 排查「46 blocks extracted but 0 translated」

**症状**：扩展端翻译 langchain.com 文章报 500 `Translation produced no results`。
线上 `/fanyi/page/check?url=...` 返回 204（无缓存），所以确实走翻译而非读缓存。

**复现**：向线上 `POST /fanyi/page` 发一个 1 block 的最小请求、`apiKey` 用无效值，
返回的错误形态与用户贴的一字不差（只是 blocks=1）。即「上游调用失败」被吞成了
「0 译文」，客户端只能看到笼统的 `provider may be unavailable or prompt was filtered`。

**四处静默降级**（`lib/translate/pipeline.ts`）：
1. `translateChunk` 的 provider catch 直接 `return cachedBlocks`，不抛也不记账；
2. 解析 catch 返回空 Map；
3. `processTranslationWithCheck` 对无法修复的响应也返回空 Map（不抛）；
4. `mergeSegmentTranslations` 在分段组不完整时丢弃全部已译片段（有意设计，但无诊断）。
任一覆盖全部 chunk → `translatedBlocks=0` → app.ts 的 500。

**修法**：新增 `TranslationDiagnostics`（provider / totalChunks / failures），随
`translateChunk → translateChunksWithRetry → runTranslationPipeline` 传递；
四种降级各记一条 `stage`（provider/parse/empty/merge），聚合成 `failureDetail`，
经 `TranslateUrlResult` 透到 `/fanyi/page` 与 `/translate/url-page` 的 500 detail。
摘要对 `sk-...` 脱敏。部分成功时不带 failureDetail，保持原有降级语义。

**验证**：tsc 干净；vitest 843/843（新增 6 例）；wrangler dry-run 构建成功。
本地 `.dev.vars` 的 DEEPSEEK_API_KEY 是 `sk-...test` 占位符，不能代表生产/扩展端密钥。
修复尚未部署（wrangler 未登录）；部署后重试即可在扩展报错里看到具体上游错误。
