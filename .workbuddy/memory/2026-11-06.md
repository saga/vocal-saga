# 2026-11-06

## 09:35 排查 KV PUT 超过 1000/天

**根因**：翻译缓存按「每个文本块一个 KV key」写入。`lib/translate/pipeline.ts` 在
`translateChunk` 里对每个块调 `cacheTranslation(itemKey, ...)`，再写一条 chunk 级 key。

实测（46 段、单 chunk 的文章，注入计数 storage 跑 `translateChunk`）：
- 首次翻译：**47 次 put**（46 块 + 1 chunk），47 次 get
- 再次翻译（chunk 命中）：**仍 46 次 put** —— `pipeline.ts:206-220` 命中后把每个块回填一遍，
  这些 key 上轮已写过，属于纯重复写

换算：1000 次/天 ≈ 20 篇中等长度文章。`/api/translate/document/segments` 按段写，
一章 300 段 ≈ 300+ 次，是更大的放大器。

其它写点：`cacheManager.ts:74` 读到过期条目顺手 delete（计一次写）；
`clear()`（`:114`）对所有 key 逐个 delete。`CloudflareKVStorage` 是唯一落地点。

**注意**：`/fanyi/page/check` 已有 D1 页级缓存挡住重复访问，能走到 pipeline 的多是
新页面或内容变化 → 块级缓存基本全 miss，却照样全量写，收益与成本严重不匹配。

**待选方案**：A 去掉块级缓存只留 chunk（1 写/页）；B 块级缓存搬 D1（10 万行写/天）；
C 每页一个块字典 key（2 写/页，需把页面标识传进 translateChunk）。用户尚未选定。

**已按方案 A 修改（本次）**：
- `pipeline.ts` 的 `translateChunk` 删掉逐块读/写与 chunk 命中后的块回填，只保留 chunk 级一次读、一次写；
  provider 失败时返回空 Map（原先是返回已命中的块），重试逻辑不变。
- 删除 `tests/incrementalBlockCache.test.ts`，新增 `tests/chunkCacheGranularity.test.ts`（4 例：
  46 块只读 1 次写 1 次、命中不回写、retry 不读不写、skipCache 只写不读）。
- 复测：46 段文章 put 47 → **1**；命中时 0 写。
- ARCHITECTURE_SUMMARY.md 的「翻译块级缓存」改为「翻译 chunk 级缓存」。
- 代价：改一段要重译整个 chunk（≤1 万 token）。若以后要增量复用，走 D1 批量写。
