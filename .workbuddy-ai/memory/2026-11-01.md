## 翻译上下文膨胀分析（只诊断，未改代码）

产出：`TRANSLATION-CONTEXT-BLOAT-ANALYSIS-2026-11-01.md`（仓库根目录）

结论：run `3bd43da3` 单批 5 段原文 6,901 字符，TranslationBrief 101,842 字符，user prompt 109,393 字符，原文只占 6.6%。

根因（按影响排序）：
1. `translationBrief.ts:398-425` `recentExamples` 明确不设数量/字符上限（注释写死 "Do not impose a fixed number/character budget"），只靠 Jaccard ≥ 0.85 去重 → 同章 134 条已采纳译文全量注入（75,261 字符 = prompt 的 69%）。
2. `translationBrief.ts:345-371` 候选 SQL 的 `OR s.context_path IN (当前章)` 分支把整章历史译文无条件拉进候选，只靠 `LIMIT 1200` 兜底。
3. `translationBrief.ts:14` `MAX_TRANSLATION_BRIEF_CHARS = 1_000_000`；`:749-752` 明确把 `strategy.contextBudgetChars` 当 legacy 忽略 → UI 上的「上下文预算」是空转旋钮，`budgetTrimCount` 恒为 0。
4. `contextGraph.ts:2459-2466` 图内候选有 `appearsInContext` 过滤，但最终 82 条 `nameMappings` 来自项目实体表整表，无逐批可见性判断 → 只有 2 条出现在本批原文，`protectedCanonicalTermCount = 0`。而 `voiceContext.entities` 同一份记忆只留 5 条（两套过滤不一致）。
5. `precedingSegments` 的 4 段 100% 包含在 `recentExamples` 里，未做差集。

成本实证：examples 32 → 134 使审校 input token 从 24.7k → 49k–51.5k（任务不变）。batch 2 仅 2 段却 208,326 input tokens（6 turns），比 5 段的 batch 1 还多一倍 —— 上下文按 turn 重复计费。

关键数据查询方式：`translation_briefs` 表有 `brief_chars` + `brief_json`；`project_events` 的 `batch.prompt.ready` 有 `sourceChars` / `userPromptChars` / `protectedCanonicalTermCount`，`model.usage` 有 `totalInputTokens` / `numTurns`。

## 日志覆盖度审计 + 修复（已实施）

审计结论：DB（`project_events`）链路完整，**文件日志不完整**，3 个硬缺陷 + 6 处内容缺口。

硬缺陷：

2. `projectRoutes.ts` 的 `routeError` 与 `middleware.sendApiError` 都不打日志 → 文档 API 全部 4xx/5xx 只剩状态码。实证 17 次 `GET /api/documents/projects/<id> → 413` 无任何原因。

信噪比倒挂：`document-projects` 774 行里 763 行是同一句 `literary memory validated`，而项目创建/导入 0 行。

## 速度分析（第二轮日志，报告：`TRANSLATION-SPEED-ANALYSIS-2026-11-01.md`）

结论：上下文膨胀**已修好**（brief 101,842 → 10,058–19,271；recentExamples 134 → 2），但慢的根因换成了审校。

实测 run `5034b08b`（38 段/4 批/pool=4）：386s = 翻译 102s + 审校 332s（串行），翻译结束后还空转 284s 等审校。

四个原因：
1. `translationAgent.ts:1656-1658` 把 medium 强度的 `reviewConcurrency` 钉死为 `1`（上一轮引入的回归），项目配置的 2 和 env 的 4 全被覆盖。
2. 审校跑 `glm-5.3-flash`（~57 tok/s），翻译跑 `deepseek-v4.1-flash`（~195 tok/s），**差 3.4 倍**。`accuracyReview.model` 换掉是单点收益最大的一项。
3. 每次调用 `numTurns=4`（maxTurns=5）；`thinkingMode=enabled/budget=8192` 导致 30–90s 零输出。
4. 每批固定 6,723 字符样板（styleGuide 3,937 + 编辑画像 1,106 + 近例 ~1,355），4 批重复 ~26,900。

新发现的日志/代码缺陷：
- `translationAgent.ts:2556` `' · ' + finishedUsage` → `[object Object]`（`summarizeTurnUsage` 返回对象）。
- `model.usage`/`batch.prompt.ready` 记的是 `agent.model`（glm-5.3-flash），实际跑 `taskProfile.model`（deepseek-v4.1-flash）→ **审计账本上的模型名是错的**。
- `runner.ts:39` `isWorkflowManaged(sessionScope)` 直接 return，导致**文档翻译调用在文件日志里完全没有记录**（无耗时/无 token）。
- `voiceContext.ts:773` `largestSections` 没排序，永远打印同一组小字段。
- `usage.ts:80` `totalInputTokens` 双重计数（网关返回 `cache_read == input`，6/6 次都相等）。
- `nameMappings` 可见性闸门算出 0 条（43−40−1−2），brief 却注入 11 条 candidate（2,100 字符，strong=0）——两条管线不一致。
- `contextBudgetChars=18000` 是死设置（b1 18,750 超了但不裁剪）。

## 实施（08:50 完成，330 测试通过 / tsc 干净）

核心修复：**审校闸门可扩容**。`createConcurrencyLimiter` 改为返回 `ConcurrencyLimiter`（带 `setConcurrency`/`getConcurrency`/`pending`）；`executeRun` 在翻译循环结束后把闸门抬到 `min(poolSize, LOCAL_AGENT_DOCUMENT_REVIEW_DRAIN_CONCURRENCY)`（后者默认 64），写 `review.drain.expanded` 事件 + `review drain` 日志。medium 强度不再硬编码 reviewConcurrency=1。

日志修复：`run finished` 用 `JSON.stringify(usage)`；新增 `resolveEffectiveTaskModel()`，`model.usage`/`batch.prompt.ready`/`model.call.failed`/`batch.model.response` 记生效模型 + `requestedModel`；`runner.ts` 去掉 `isWorkflowManaged` 的提前 return（文档翻译终于有调用级日志）；审校 usage 回传并写 `model.usage`(stage=review)、计入 run 合计；`literary-review` 行加 duration/turns/model；`largestSections` 按大小排序。

上下文：`mergeShortTailBatch`（尾批 ≤ maxBatchSegments/3 且不越 maxBatchSourceChars/章节才合并）；`contextBudgetChars` 超预算时记 `contextBudgetExcessChars` 并在日志标注"未裁剪"。

**刻意没改**：`totalInputTokens` 相加语义有测试锁定（server.test.mjs:801），网关 `cache_read==input` 是报告口径问题不是代码 bug；`/segments` 轮询被 request-log.test.mjs:26 明确归为 one-off；`nameMappings` 可见性闸门与"本批未提及"过滤器语义不同，不赌；`styleGuide` 移出 brief 需单独质量对照。

**用户需手动改**：项目 prompt revision 里 `accuracyReview.model` 是 `glm-5.3-flash`（代码默认已是 deepseek-v4.1-flash）、`translation.thinkingMode` 是 `enabled`（默认 disabled）。`.env` 的 `LOCAL_AGENT_POOL_SIZE=4` 偏小。

## 环境注意

- 本机 `bash` 里的 `grep` 对多模式/转义经常静默返回空（连 `grep -rn "boot failed"` 都空），改用 Grep 工具或 `node -e` 扫描，别据此判断"代码里没有"。
- 项目数据不在 `local-agent.sqlite`（只有 request_history/translation_cache/document_sessions/service_settings）。每个项目的库在 `~/.vocal-saga-local-agent/documents/<project_id>/project.sqlite`，`project_events` / `translation_briefs` / `run_segments` 都在那里；`documents/catalog.sqlite` 的 `document_projects` 表负责 project_id → db_path。
- `project_events.created_at` 是 UTC，文件日志是本地时间，差 8 小时，别当成两次运行。
