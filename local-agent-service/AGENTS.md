# AGENTS.md — Local Agent Service

## 翻译质量总原则：信、达、雅同时达到

翻译不是先做准确性、再把文学性当作可选润色。**信、达、雅是同一份译文必须同时追求的质量目标**：

- **信**：准确传达事实、语义、否定、时态、视角、指代、语气、潜台词与有意保留的歧义；不漏译、不误译、不增写。
- **达**：表达自然、清楚、顺畅，符合目标语言的语法、语用和阅读习惯；不照搬源语言语序，不制造翻译腔。
- **雅**：尽可能保留原作者的叙述声音、文体、节奏、修辞、意象和人物对白差异；不是把所有作品润色成同一种“漂亮中文”，也不是擅自华丽化。

三者共同约束译文，不采用“准确性永远高于文学性、文学性只是可选项”的固定层级。发生张力时，先守住原文事实与叙事意图，再通过调整句法、节奏、措辞和语气寻找兼顾三者的表达；不得以增删信息换取文采，也不得以逐词对应为借口保留生硬表达。原文已经自然、有力且准确时，不为体现审校工作而改写。


## 服务定位与责任边界

`local-agent-service` 是运行在用户本机 macOS（当前主要目标为 MacBook）的长任务 AI 服务，属于 `vocal-saga` 仓库，但**不是 Cloudflare Worker 的一部分，也不能按 Cloudflare Worker 的资源与生命周期假设设计**。它由 Node.js 运行，默认仅监听 `127.0.0.1:8789`，通过本机 HTTP API 与 `fanyi-extension` 协作。

本服务面向需要更高质量、较长上下文、持久化状态和 Agent 编排的任务。对于文档与小说翻译，**翻译质量优先于响应速度**；允许长时间运行、分批执行、审校、候选比较和选择性返工，但必须有可观测状态、持久化进度、可恢复性和明确的停止边界。

## 本服务负责

- 调用本机可用的 AI Runtime/Agent，例如 Workbuddy/CodeBuddy SDK、OpenCode CLI；管理 Provider/模型选择、会话边界、工具调用、超时和失败分类。
- 完整支持 EPUB/PDF 等文档翻译工作流：项目与来源版本、稳定分段、批次执行、断点恢复、候选译文、采纳译文、人工修订、审校发现和事件记录。
- 维护文档级上下文：书籍/项目记忆、章节与场景摘要、术语表、实体映射、人物声音档案、人物关系与称谓规则、已确认的译例。
- 运行按任务类型选择的 Pipeline 和 Prompt，包括初译、结构/忠实度检查、术语一致性检查、文风/人物声音审校、候选比较和有条件的局部返工。
- 将任务状态、阶段事件、错误、耗时、Provider/模型元数据和持久化检查点提供给扩展，使 UI 关闭或刷新不致丢失已经保存的项目进度。
- 为长期质量改进提供可重复的离线评测、黄金样本、回归测试和 Prompt/策略版本记录。

## 不负责

- 不承担浏览器 UI、页面 DOM 操作、浏览器权限、网页布局恢复或扩展生命周期管理；这些属于 `fanyi-extension`。
- 不依赖 Cloudflare Worker 的执行时限、内存或计算预算，也不将本机服务打包成 Worker Handler。
- 不将所有翻译请求都强制升级为长时间 Agent 任务。普通网页段落或短文本的低延迟翻译应使用 Cloud API 或适合的轻量路径，除非用户明确选择本机服务。
- 不以无条件多 Agent/多轮审校作为默认。额外调用必须针对预期质量收益、风险或检测到的问题；应允许简单任务走轻量 Pipeline。

## 统一执行管线与任务策略

本服务对所有本地长文翻译只维护一条**项目级执行管线**：阅读页的继续翻译/强制重译、Agent Workspace、CLI 和项目 API 必须进入同一套 Document Project / Run 生命周期，由 `startProjectTranslationRun → executeRun → processBatch` 统一执行。界面入口只能选择当前页/章节/选定片段/全部或过期片段等 Run scope，不得自行执行另一套本地翻译循环、另造人物记忆更新机制或在扩展端直接修改项目记忆。

统一的是调度、持久化、恢复、结构验证、候选译文、审校、事件与质量审计边界，不是把文学、技术文档和短文本强行使用同一份 Prompt。任务差异必须表达为同一管线中的明确策略/Prompt 配置，而不是按入口分叉。阅读页（截图中的“继续翻译下一待译页/强制重译当前页”）也必须通过项目 API 创建或恢复 Run；不允许仅 Agent Workspace 才享有 TranslationBrief、上下文增量或质量检查。

文学初译的统一响应必须包含 `translations`；`context_delta` 是可选的附属记忆观察，不得成为初译负担。服务端独立验收两部分：译文按 segment ID 校验和保存；上下文增量只有在引用当前批次真实 segment ID、连续原文引文可验证，且译文提及的 target surface 确实存在时才接受。上下文增量在同一波次冻结，不得影响同波其他批次；波次完成后按原文 ordinal 合并，下一波才可读到候选。模型新增内容通过来源/结构校验后以 `model-default` 默认采纳并参与后续翻译；低置信度观察作为弱提示，不得伪装成用户确认，也不得覆盖 `user-modified`、`user-confirmed` 或 `user-rejected` 决定及人工译文。详细契约见 [本地统一翻译 Pipeline 架构](../docs/TRANSLATION_PIPELINE.md) 和 [ADR-0001](../docs/adr/0001-unified-local-translation-context-delta.md)。

任务路由应明确表达用户需求，而不是只按输入长度选择同一套通用流程。

| 任务类型 | 目标与策略 | 建议 Pipeline |
|---|---|---|
| 小说/文学长文 | 信、达、雅同时达到；保留作者风格、人物声音与叙事连续性 | 相关上下文 → 高质量初译 → 默认一次合并双语审校（同时检查准确性、自然度和文学表达）→ 仅修复有证据的问题 → 持久化采纳；高风险或用户选择强审校时才拆分为专项审校 |
| 一般 EPUB/PDF/长文档 | 完整、准确、术语一致，保留结构与可恢复性 | 文档解析与稳定分段 → 文档/章节上下文准备 → 分批初译 → 结构与完整性验证 → 风险片段审校 → 选择性返工 → 导出/同步 |
| 技术文章或网页长文 | 忠实、术语和代码一致，避免不必要的文学润色 | 轻量上下文 → 分块翻译 → 术语/格式检查 → 对异常块定向重试 |
| 短文本/选区 | 简洁、直接、快速完成，不引入长篇规划 | 单次翻译 → 结果结构与空输出检查；仅在失败时进行有限重试 |
| 需要复杂工具的翻译研究/编辑任务 | 允许多步骤与 Agent 工具调用，结果可追踪 | 任务计划 → 有界工具调用 → 证据/候选记录 → 结果验证 → 汇总与持久化 |

这些是策略模板，不是硬编码的唯一流程。根据源语言、目标语言、文体、文档结构、用户质量选项、模型能力与实际失败信号选择或调整步骤。

## 原始文档解析与 Context Graph 边界

- EPUB/DOCX/PDF 等原始文件的解析和预处理必须位于 local-agent-service，不得要求 fanyi-extension 先将整本书拆成片段；本机服务提供独立 CLI/API 入口。本约束不意味着可以顺带修改扩展，本项目任务若明确要求不动扩展，就只提交服务端变更。
- 支持纯文本 EPUB、DOCX、TXT、Markdown、HTML，以及带文本层的 PDF。PDF 通过 Poppler `pdftotext` 做文字提取；当前不实现 OCR，也不能把“未提取到文字”静默视作成功。
- EPUB 按 OPF manifest/spine 顺序读取，保留章节/内容路径、标题与稳定片段 ID。解析必须有文件大小、解压大小、片段数、超时及路径安全边界；不得将 ZIP 条目解压到用户可控的任意路径。
- Context Graph 是来源版本级的持久化状态，SQLite 为事实来源。模型生成的人物、别名、实体、关系与摘要先经过服务端来源证据校验；校验通过后默认以 `model-default` 生效，证据强度决定置信度和使用范围。证据必须包含稳定 segment ID 和能在对应原文片段中验证的连续引文；模型自称“确认”不能代替证据校验，机器默认采纳也不能伪装成人工确认。
- 用户删除/拒绝人物、实体或关系时，服务端必须在同一 SQLite 写事务中更新 Context Graph 节点/边状态、LiteraryMemory revision 和项目事件；扩展通过 `/context-graph/review` 的 batch `items` + `memory` 一次提交。任何校验或持久化失败都必须整体回滚，禁止两个接口分步写入造成部分成功。
- LiteraryMemory 可见列表删除后，必须保留隐藏 `rejectedItems` tombstone（实体按规范名/别名与 kind 匹配，关系按 subject/predicate/object 匹配）。服务端 sanitize、Extension sanitize/merge 和 translation context delta merge 必须保留 tombstone 并先过滤对应活动项；只有用户明确编辑/重新建立同一项才清除对应 tombstone。不得只依赖当前 Context Graph node/edge ID，因为后续分析可能生成不同 ID。
- Run 创建必须在 SQLite 写锁内重新校验 source revision、Prompt revision 和 LiteraryMemory revision；快照准备期间任何一项变化都返回 409，不得静默绑定旧快照。
- `failed` scope 必须 JOIN 失败记录所属的 `translation_runs`，限定当前 `source_revision_id` 并匹配当前 `source_hash`；当前 fingerprint 已自动采纳的译文和当前人工译文不得因历史失败再次入选。旧 fingerprint 的机器译文仍可进入修复范围。
- `maxModelAttempts` 表示单个 batch 的模型调用总次数，包含首次调用；重试分组不得突破这个总预算。默认 2 次时，首次调用后最多再发起一次包含全部缺失 ID 的定向补齐调用。
- 原始文件更新必须先完成临时文件写入和原子 rename，再在 SQLite 事务中登记文件 hash/size/path 并切换 current source revision。数据库提交失败必须清理新文件；任何路径都不得先切换 revision 再尝试写原始文件。
- Run 必须保持 running 直到本轮 context delta 与 LiteraryMemory 的合并事务完成，再进入 awaiting_acceptance 并自动采纳。awaiting_acceptance 是未完成最终化状态，阻止创建下一 Run；服务重启时自动恢复 context-memory merge 与 candidate acceptance。
- Candidate acceptance 必须验证 Run source revision 仍是当前版本，并保护同一 source hash 上所有更新的 accepted result（agent/imported/manual），不能只保护 manual。旧 Run 延迟恢复不得覆盖新 Run 的已采纳结果。
- 中文单语文学编辑结果只能作为 provisional edit。必须由后续双语审校按 segment 明确覆盖并返回完整非空译文后，才可写入候选；以双语审校最终文本为准。未覆盖、missing、空/格式无效、retry 失败或审校调用异常的 segment 必须自动恢复初译，并确保 provisional edit 不进入候选、context delta 或 LiteraryMemory。部分覆盖按 segment 分别处理；若双语复核将某项改回初译，对应中文单语 finding 自动 dismissed 并记录 `automatic-bilingual-review-reverted`，不留待人工处理的 pending finding；不得要求用户点击确认。
- 全书图谱、原文证据、章节摘要与人物/关系候选必须留在服务端；不得复制到扩展 LiteraryMemory。扩展轮询使用轻量 /context-graph/status 投影，不轮询完整节点/证据载荷。
- 长篇/全书文学翻译必须先完成当前来源版本的全书预处理；小范围显式选段（最多 12 个有效片段且源文合计不超过 6,000 字符）在没有正在运行的全书分析时允许使用片段级上下文直接翻译。服务端必须复核 Run 仍绑定项目当前原文版本；已存在匹配图谱时优先复用，正在运行的分析仍等待。文风字段不齐不是翻译门槛。扩展通过轻量 /context-graph/status 投影展示状态，不复制图谱或实现第二套分析算法。详见 ADR-0005。
- 抽样不得只取开头、章节标题或最近章节。长文档至少覆盖开头/中部/结尾、分布式章节样本以及对白或专名较密集的片段；其余章节可以先生成抽取式摘要，再逐步补充模型摘要。
- 小说预分析必须先对全部 source segments 做确定性低成本扫描，再进行自适应抽样。主质量基线按英文原文翻译成中文设计；扫描结果包括章节分布、英文首字母大写姓名候选、对白信号、重复英文句子/引语线索；长文默认最多 72 个样本，单样本最多 850 个原文字符，短文档在预算内全量采样。
- 长文样本计划需保留开头/中部/末尾、跨章节分布，并尝试对高重要性名称候选补采样早期/中期/后期提及，再补充重复表达与对白密集片段。抽样理由与扫描计数应持久化到 Context Graph run progress，便于观察覆盖范围；不得只记录一个 sampleCount。
- 英文姓名扫描是首字母大写启发式，不是 NER：句首普通词可能被误判，非典型拼写、化名、称谓与同名异人也可能漏检。扫描统计和候选名称只能指导采样，不是事实；每个被保存的图谱结论仍需来自被采样片段的可验证原文引文。证据查询应返回 source segment ID、章节路径和原文顺序。
- 维护合成小说质量回归集，至少覆盖漏译、名称/别名漂移、重复台词不一致、后文揭秘泄漏；人物声音需另有人工盲审样例，不能用自动流畅度或一个总分代替。合成样本只能验证确定性规则和失败控制，不得冒称是真实模型效果基线。
- 翻译时动态检索只注入当前批次真正匹配的人物/实体、相关关系与当前及之前章节摘要；禁止将整本书的所有记忆无差别塞入每个 Prompt，禁止注入后续章节摘要造成剧透。上下文必须设预算并有可观测的命中计数。
- Context Graph 的来源版本、节点/边状态、结构化属性、证据和章节摘要必须影响文学运行指纹；图谱预处理或人工审核不能在翻译 Run 执行期间修改图谱，避免同一个 Run 的不同批次看到不同版本的上下文。
- 每个文学批次构造并持久化一个版本固定的 TranslationBrief；初译和实际运行的 Reviewer 共用同一快照。快照包括受时间边界过滤的 glossary、前文、Context Graph 与 voice context，并记录 source/prompt/memory revision、source segment IDs、context hash、context size、知识边界和检索条目计数。检索按原文证据、当前片段相关性、时间边界与冗余决定注入内容。`contextBudgetChars` 是整个可选上下文的目标预算，按相关性裁剪历史译例、摘要、低相关画像和弱候选；用户确认译名、Run 规范译名、当前原文及必要的前文/术语不得被低优先级材料挤掉。1,000,000 字符是异常安全上限，不是检索目标；若核心上下文仍超出配置预算，应记录超额诊断，不得静默丢弃关键内容。Reviewer 不得为自己另造更宽或不同版本的上下文。
- 时间边界按来源 ordinal 定义，而不只按章节名：图谱节点/关系只有在所有存储证据都早于当前批次第一个 source segment 时才能注入。只允许前两章的完整摘要；当前章节只允许用批次之前的原文片段构建前缀摘要，禁止使用包含当前批次之后内容的完整章节摘要。
- 质量审计必须能在整书范围内定位缺失译文、用户确认术语漂移、重复原文表达译法差异，以及已有 Reviewer 标注的人物声线/文风问题。启发式发现只定位问题，不自动统一重复表达；有原文/译文证据的 Reviewer 修改自动形成 Run 候选，Run 最终化自动采纳有效候选，用户可事后修改或拒绝。
- 定点返工必须创建新的 selected-ID Run，不覆盖较新的已采纳/人工译文；有效候选在 Run 最终化时自动采纳，用户修改/确认/拒绝优先。返工报告与 Run 必须保存来源版本及父运行关联，来源变化后旧报告不得发起返工。
- M4 的前后对照必须验证相同来源版本、源/目标语言和精确的 segment ID 集合，拒绝比较仍在运行/暂停/取消的任务。记录 model calls、已知 prompt 字符和已知调用时延；若 Provider 没提供 token/billing 数据，不得推算或声称真实费用。A/B 映射在每个样本完成 overall 人工盲评前不得披露。
- CLI、API 和 README/AGENTS 必须一致。服务端直读入口不会自动改变扩展的现有阅读流程；没有对应的扩展集成代码就不得声称扩展已开始使用新导入器。

## Prompt 设计规则

1. 按任务类型维护独立、可版本化的 Prompt 与策略；不得用单一“通用翻译 Prompt”处理短文本、技术文档和小说。
2. 小说 Prompt 应明确叙述视角、人物身份、语域、口头禅、句式偏好、称谓和人物关系变化；人物声音资料是指导约束，不是机械地把所有台词改成夸张口癖。
3. 技术文档 Prompt 应优先保证事实、术语、标识符、代码、表格和结构忠实，不应套用文学润色策略。
4. 初译与审校可以使用不同任务指令，但不要求每段机械经历多个 Reviewer。默认合并审校应同时检查准确性、中文/目标语言自然度和作者风格；只有强审校或明确高风险场景才拆分专项阶段。Reviewer 必须指出可定位、可验证且确实影响译文质量的问题；风格判断不能沦为个人偏好，也不能因为主观性就一律降为可忽略。
5. Prompt、模型、语言方向、术语表/项目记忆版本及 Pipeline 版本必须进入适当的运行记录和缓存指纹。关键输入变化时应失效相关缓存。
6. 只将必要的章节/场景摘要、相关人物卡和相关术语传入当前批次；避免把全书原文或完整运行历史重复塞入每次调用。
7. JSON/结构化输出必须进行解析、完整性和语义验收；解析失败或被截断的内容不能当成成功译文缓存或采纳。

## 质量优先，但必须可控

- 对长文档可以采用分批并发、独立会话、Reviewer 队列、候选比较与局部返工；并发度必须考虑本机内存、模型 Provider 限额和会话隔离，不能假设越多并发质量越高。
- 以质量收益决定额外调用：准确性与文学表达都必须达标。默认一次合并双语审校同时覆盖误译/漏译/术语、翻译腔、语气/节奏和人物声音；不要默认每批再追加独立文风调用。只有合并审校无法兼顾、发现明确风险或用户选择强审校时，才拆分专项 Reviewer。
- 长任务必须支持持久化检查点、可重入/幂等的批次处理、取消信号和明确的停止边界。停止后不能继续悄悄发起新的模型调用。
- 所有模型与工具调用都应记录阶段、耗时、Provider/model、输入版本、结果状态和错误类别；日志应便于按 request/run ID 关联，不得记录密钥。
- 缓存命中必须验证原文版本、语言方向、Prompt/Pipeline 版本、模型配置以及相关项目记忆版本；不得让旧缓存覆盖人工修订。
- 文档任务的“完成”必须由持久化状态和验收结果决定，不能仅以某个请求返回 HTTP 200 或某个批次结束为准。

## 阅读页与 Agent Workspace 一致性约束

- 阅读页“继续翻译下一页/下几页”“强制重译当前页”和 Workspace/API/CLI 必须调用同一 project run executor；新增 UI 操作只能映射到 scope 或策略配置，不得新增平行翻译实现。
- 服务端统一生成并持久化 TranslationBrief，统一处理结构化初译、证据校验、候选提交、审校、上下文增量、取消/恢复与质量审计。扩展负责显示进度和呈现已保存状态，不负责合并模型上下文增量。
- 对局部/强制重译同样使用统一契约；上下文记忆仍按来源 ordinal 过滤，不得因“强制”绕过上下文证据、来源版本或人工采纳边界。
- 修改阅读页触发路径时，必须增加覆盖 project API 到同一 Run executor 的回归测试，并核对事件/Run 状态而不能只验证按钮反馈。

## 安全与运行约束

- 默认只监听 loopback；不得通过局域网、反向代理或隧道公开本机 Agent API。
- 遵守输入大小、存储配额、超时和清理策略。长任务可以长，但不能无限制积累上下文、并发任务、缓存或日志。
- 不得静默回退到 Cloud API，也不得将远程结果标记成本机 Agent 结果。Provider 不可用时应明确报告失败或执行经过用户/产品策略允许的备选方案。
- 对 API、项目、运行、批次和候选的状态变更增加测试；尤其覆盖重启恢复、重复提交、取消、部分完成、缓存失效、损坏 JSON 和模型输出不完整。
- 在修改前先阅读相关 ADR、README、现有实现和测试；优先复用已有 Document Project、SQLite、事件与恢复机制，不另造平行体系。

## 全流程审计与原始来源保全（ADR-0002）

- 必须遵守 [ADR-0002](../docs/adr/0002-local-translation-audit-ledger-and-source-preservation.md)。最终译文、当前状态、日志摘要都不能替代逐次调用账本。
- 完整分段原文必须持久化；存在原始文件时保存原始字节、SHA-256 和服务管理的数据路径。只有 segments 的项目必须显式标记为 segments-only。
- 初译、定向重试、每种 Reviewer、全书分析和质量修复都要保存实际输入快照、输出、校验、模型/Provider、阶段、时间、错误与重试关联。审校输入须能重建对应原文和候选译文。
- 重要状态转换必须持久化；失败的审计写入不能静默降级为成功。重试、修订和人工采纳不得覆盖历史证据。
- 设置页路径必须来自服务实际运行配置，不得由扩展猜测 home 路径，也不得暴露密钥。
## 无感自动运行：99.9999% 的任务无需人工介入（最高产品原则）

**这是 local-agent-service 的顶层产品原则，适用于整个服务的运行期，而不只是翻译主流程。** 文档项目、小说翻译、Context Graph 预处理、记忆提取与合并、Reviewer、质量审计与修复、普通 Agent/Skill/Tool 调用、后台任务、失败恢复和服务重启，均必须遵守本原则。

- **目标是至少 99.9999% 的已受理任务从启动到结束不需要任何运行期人工主动介入或审核。** 按已受理 Run 计，目标相当于每 1,000,000 次 Run 中需要人工介入的次数不超过 1 次。这是产品目标，不是当前已经达到的统计结论；必须通过真实运行事件和指标验证，不得仅凭存在自动化代码就宣称达标。
- 本原则中的“人工介入”包括：要求用户点击继续、重试、恢复或重新分析；逐批、逐段或逐阶段确认；审核或批准模型结果、候选译文、人物/实体/关系/记忆、审校发现或自动修复；要求用户在多个正常执行选项间反复作选择；把可恢复错误放进等待用户处理的队列。只要一个已启动的正常任务必须等用户执行某个动作才能继续，就属于人工介入。
- 用户主动发起新任务、主动取消/停止任务、明确编辑或拒绝已有结果，属于用户对产品的正常控制，不计入人工介入。首次安装、一次性环境配置、提供源文件和启动任务所必需的输入也不计入运行期介入；不得把这些初始设置扩展成每次任务都要确认的步骤。
- **任务一旦被服务受理，服务端就拥有完整执行生命周期。** 不依赖浏览器页面持续打开、扩展持续轮询、Agent Workspace 保持活动或用户点击后续按钮。所有阶段推进、状态持久化、验收、采纳、重试、恢复和收尾均由服务端自动完成。
- 正常执行路径不得引入人工审批闸门。模型输出、记忆、审校发现和返工结果应由服务端执行来源、结构、版本、证据和语义校验；通过校验后按策略自动保存、启用或采纳。机器验证与机器默认采纳必须明确记录，不能伪装成用户确认；自动操作不得覆盖用户已修改、确认或拒绝的内容。
- 不确定或证据不足时，优先使用已有规则和上下文作保守处理：保留当前有效译文、降低候选置信度、跳过有歧义的局部记忆、将发现作为非阻塞信息记录，并继续其余可安全执行的工作。不得把普通风格分歧、低置信候选或 Reviewer 的非关键失败变成等待用户审核的阻塞项。
- 可恢复故障由服务自动处理：对超时、限流、临时 Provider 错误、结构化输出缺失、阶段中断和进程重启，使用有界重试、退避、幂等写入、持久化检查点和自动恢复。单次重试预算耗尽不等于要求用户点击“重试”；应保存可恢复状态，并由服务在退避或依赖恢复后自动重新调度。不得无限紧密重试，也不得把未完成任务标成成功。
- 恢复必须覆盖完整生命周期，而不只是把数据库状态改成 `pending`：服务重启后自动恢复未完成的 Run、批次、Context Graph 阶段、自动采纳和收尾；恢复执行器必须重新启动，避免留下需要用户在 UI 中手动 resume 的孤儿任务。重复启动、延迟模型响应和并发恢复必须幂等且有写入栅栏。
- 故障应尽可能隔离到受影响的阶段、批次或片段。某一段、某个 Reviewer 或非关键记忆阶段失败，不应使其他可独立完成的工作等待；任务最终状态必须如实区分完整、部分完成和失败，并保留未解决例外及其原因。
- 安全、权限、来源版本、数据完整性和用户已有修改是硬边界，不能为了自动化指标而绕过。只有在缺少不可替代输入、凭据/权限无法建立、来源或持久化数据损坏、存在无法自动消解且可能覆盖用户数据的冲突，或继续执行会造成不可逆/不安全操作，且不存在安全隔离或保守继续方案时，才允许要求用户决策。此类情况应限定到受影响范围，清楚说明阻断原因；不得把可恢复的 Provider、网络或模型错误包装成此类例外。
- 所有自动决定都必须可解释、可审计、可撤销。记录来源与版本、Prompt/策略/记忆 revision、模型调用、重试及恢复关联、校验结果、自动应用理由、修改前后快照和失败原因；保留用户原始修订。自动化不等于隐瞒错误，也不等于无条件接受模型输出。
- 自动化验收必须有故障注入与回归测试，至少覆盖：Provider 超时/429/5xx、结构化输出截断或缺段、Reviewer 失败、Context Graph 失败/不完整、进程在各持久化边界退出、服务重启、重试重复触发、自动采纳中断、来源版本变化，以及人工修改与自动结果竞争。测试必须证明服务无需用户操作即可恢复，或安全隔离受影响部分并继续其他工作，同时不会重复写入或覆盖用户决定。
- 持续记录并评估：无人工介入的端到端完成率、每百万 Run 的人工介入次数、每千段人工介入次数、自动恢复成功率、重试后恢复率、部分完成率、自动修复回退率、漏修率和数据完整性错误。不能只以“没有弹确认框”作为无感自动化达标依据。

**当前实现差距（2026-11-28，属于待整改项，不代表被接受的产品行为）：**

- 文学预处理在两次自动尝试后仍不完整会让 Run 失败；`API_CONTRACT_AND_LIFECYCLE_POLICY.md` 还明确规定失败/陈旧分析需要显式重新分析。这会阻断主翻译流程。
- 服务重启恢复会把中断的 Run 标记为 `failed`，错误提示要求用户在 Agent 面板恢复或放弃；虽然运行中的片段会归一为 `pending`，但当前恢复流程没有自动重新启动翻译执行器。
- 批次模型调用用尽有限重试后会留下 `failed` 片段，Run 可进入 `partial/failed`；继续执行仍依赖 `POST /runs/:runId/resume`。缺译自动返工目前也有单轮限制。
- 自动质量修复只覆盖受限的缺译场景；普通质量返工接口仍采用人工确认语义（`humanAcceptanceRequired`）。它不一定阻断主 Run，但说明审计发现到自动处置的闭环尚未完整。
- `contextGraphWorkflow.ts` 的 chapters 阶段 Prompt 仍把 `openQuestions` 描述为“需要人工确认的事项”；当前它是分析输出而非执行闸门，但会把不确定项导向人工处理语义。应改为自动核验、保留低置信度/非阻塞问题，不要求用户逐项审核。
- 现有自动化测试验证了正常候选自动采纳等局部行为，但重启后自动恢复执行器、预处理失败后无人值守恢复、Provider 故障后的自动续跑等关键验收场景尚未被证明。

以上差距不得通过降低 99.9999% 目标、把人工操作改名为“恢复流程”，或把未完成状态标为成功来规避。后续实现应逐项消除这些运行期人工依赖，并为每项修复增加自动化测试。

## 当前统一规则：默认采纳、事后纠正（2026-10-31，优先于本文旧描述）

- 模型产生的当前最佳结果在通过来源/结构完整性校验后默认参与后续翻译；不得要求用户逐项确认人物、实体、关系、声音、文风或普通审校发现。
- `model-default` 是机器默认采纳，不是用户确认。用户修改、确认和拒绝必须分别记录；`user-modified` 与 `user-confirmed` 均优先于机器默认结果。
- 用户拒绝/删除必须持久化，重新分析、记忆刷新、TranslationBrief 合并不得自动恢复。不得仅删除 UI 或 LiteraryMemory 投影而让 Context Graph 原记录继续注入。
- 证据不完整只影响置信度、可用范围和约束强度，不得仅因文风字段、画像维度、关系证据覆盖不完整而阻断翻译。
- 保留原文版本、语言方向、来源绑定、未来章节隔离、译文写回位置和数据完整性等硬约束。只有缺少不可替代输入、数据损坏或执行无法继续等技术异常才暂停。
- 自动应用必须保留来源与版本记录，且不得覆盖用户修改；用户可以事后修改或拒绝。
- 任何旧段落中要求“候选必须人工确认”“证据完整后才能启用”“风格字段必须齐全”的规则均已被本节取代。


## Standalone Agent Chat Boundary

- Browser/webpage chat uses `GET /api/agent/capabilities`, `GET /api/agent/skills` and `POST /api/agent/chat`.
- This general-purpose chat API must remain independent of Document Project / Translation Run / literary translation and review workflows. Do not create a fake document project to execute ordinary chat.
- Agent Skills are owned by `local-agent-service/skills`. The extension sends Skill IDs only; the service resolves and reads the corresponding `SKILL.md`. Never accept client-provided Skill paths or Skill bodies.
- Keep provider, model, thinking mode, effort and selected Skill IDs explicit in each request. Workbuddy and OpenCode use the shared Runtime adapters, but provider-specific reasoning controls must be mapped by the service.
